¿Qué se Sincroniza?

✅ La sincronización es bidireccional: el panel lee datos de MeLi y también puede enviar cambios (precio, stock, estado). Todo ocurre en background vía Jobs en Queue.

Tipos de datos sincronizados

TipoDirecciónJobFrecuencia automática
Productos MeLi → Panel SyncProductsJob Cada 30 min
Órdenes MeLi → Panel SyncOrdersJob Cada 10 min
Clientes MeLi → Panel SyncCustomersJob Cada hora
Estadísticas BD interna CalculateStatisticsJob Cada hora
Producto individual MeLi → Panel — Manual
⏰

Sincronización Automática (Scheduler)

Comandos programados

sync:products
Cada 30 minutos
Trae todos los ítems activos, paused y closed desde MeLi. Crea o actualiza en la BD local.
sync:orders
Cada 10 minutos
Órdenes de las últimas 24h. Crea clientes si no existen. Sincroniza order_items con product_id.
sync:customers
Cada hora
Refresca nombre, email, teléfono y nickname de todos los clientes existentes en la BD.
calculate:statistics
Cada hora
Recalcula sales_statistics y product_statistics agrupando órdenes pagadas (status=paid).

Activar el Scheduler (desarrollo)

El scheduler de Laravel necesita correr continuamente. En desarrollo hay dos opciones:

# Opción A: Ejecutar una vez manualmente
php artisan schedule:run

# Opción B: Simular el scheduler en loop (recomendado en dev)
php artisan schedule:work

Configurar el Scheduler (producción)

Agregar una sola entrada al crontab del servidor. Laravel se encarga del resto:

# Editar crontab
crontab -e

# Agregar esta línea (reemplazar /ruta/proyecto por la ruta real)
* * * * * cd /ruta/proyecto && php artisan schedule:run >> /dev/null 2>&1
ℹ️ El cron del sistema corre el schedule:run cada minuto, pero cada comando tiene su propia frecuencia definida en routes/console.php.

Definición de la programación (routes/console.php)

Schedule::command('sync:products')->everyThirtyMinutes();
Schedule::command('sync:orders')->everyTenMinutes();
Schedule::command('sync:customers')->hourly();
Schedule::command('calculate:statistics')->hourly();

Webhooks en Tiempo Real

⚡ MeLi envía notificaciones instantáneas cuando ocurre un evento (nueva orden, cambio de precio, etc.). El panel responde en menos de 1 segundo y procesa en background.

Endpoint del webhook

POST /api/webhooks/mercadolibre
# Sin autenticación JWT — usa firma HMAC-SHA256
# Header: x-signature: {signature}

Flujo de procesamiento

MeLi envía
POST al webhook
→
Validar firma

x-signature
→
Responder
HTTP 200
inmediato
→

en background
→
BD actualizada
+ Evento disparado
⚠️ MeLi requiere respuesta HTTP 200 en menos de 500ms. Por eso se responde inmediatamente y se procesa en background con un Job asíncrono.

Tipos de notificaciones que llegan

topicDescripciónJob disparado
orders_v2Nueva orden o cambio de estadoSyncOrdersJob
itemsCambio en un ítem (precio, stock, status)SyncProductsJob
questionsNueva pregunta en un ítem— (solo log)
paymentsCambio en el estado de un pagoSyncOrdersJob

Configurar el webhook en el portal de MeLi

En el portal de developers de MeLi, dentro de tu aplicación, ir a Notificaciones y configurar:

URL de notificaciones:
  https://tudominio.com/api/webhooks/mercadolibre

Topics a suscribir:
  ✓ orders_v2
  ✓ items
  ✓ payments
ℹ️ En desarrollo local, usar ngrok o similar para exponer el puerto 8000 a internet: ngrok http 8000. Usar la URL HTTPS de ngrok como URL del webhook.

Queue Worker

🚨 El Queue Worker es obligatorio para que funcione cualquier sincronización. Sin él, los Jobs se encolan pero nunca se ejecutan.

Iniciar el Queue Worker

# Desarrollo (muestra logs en tiempo real, reinicia al cambiar código)
php artisan queue:listen

# Producción (más eficiente, no detecta cambios de código)
php artisan queue:work --queue=default --tries=3 --timeout=300

# Con supervisor (recomendado en producción)
# Ver configuración de supervisor más abajo

Configuración de Supervisor (producción)

Crear el archivo /etc/supervisor/conf.d/marketplace-worker.conf:

[program:marketplace-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /ruta/proyecto/artisan queue:work database --sleep=3 --tries=3 --timeout=300
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/log/supervisor/marketplace-worker.log
stopwaitsecs=3600
# Activar
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl start marketplace-worker:*

Verificar que el Queue está funcionando

-- Ver Jobs pendientes en la cola
SELECT id, queue, payload, attempts, created_at
FROM jobs
ORDER BY created_at DESC
LIMIT 10;

-- Ver Jobs fallidos
SELECT id, queue, payload, exception, failed_at
FROM failed_jobs
ORDER BY failed_at DESC
LIMIT 10;

Reintentos y Rate Limiting

Política de reintentos de Jobs

ConfiguraciónValorDescripción
$tries3Número máximo de intentos por Job
$timeout300 segundosTiempo máximo de ejecución por intento
Fallo finalfailed_jobsVa a la tabla failed_jobs + SyncFailed event

Exponential Backoff para Rate Limiting de MeLi (429)

Cuando MeLi responde con HTTP 429 (Too Many Requests), el sistema aplica espera exponencial antes de reintentar:

Request #1
429 → esperar 1s
Intento #2
429 → esperar 3s
Intento #3
429 → esperar 10s
Fallo final
// Implementación en MercadoLibreService.php
private function requestWithRetry(string $method, string $url, array $options = []): array
{
    $delays = [1, 3, 10]; // segundos de espera entre intentos
    foreach ($delays as $i => $delay) {
        $response = Http::withToken($account->access_token)->$method($url, $options);
        if ($response->status() !== 429) {
            return $response->json();
        }
        if ($i < count($delays) - 1) {
            sleep($delay);
        }
    }
    throw new MeliRateLimitException('Rate limit excedido después de 3 intentos');
}

Re-ejecutar Jobs fallidos

# Ver jobs fallidos
php artisan queue:failed

# Re-intentar todos los fallidos
php artisan queue:retry all

# Re-intentar uno específico por ID
php artisan queue:retry 5

# Eliminar todos los fallidos
php artisan queue:flush

Consultas útiles sobre sync_logs

-- Últimos 20 sync de productos
SELECT type, status, records_processed,
       TIMEDIFF(finished_at, started_at) AS duracion,
       started_at
FROM sync_logs
WHERE type = 'products'
ORDER BY started_at DESC
LIMIT 20;

-- Errores de hoy
SELECT sl.*, ma.nickname
FROM sync_logs sl
LEFT JOIN mercadolibre_accounts ma ON sl.mercadolibre_account_id = ma.id
WHERE sl.status = 'error'
  AND DATE(sl.started_at) = CURDATE()
ORDER BY sl.started_at DESC;

-- Estadísticas de sync de la semana
SELECT type,
       COUNT(*) AS total_ejecuciones,
       SUM(CASE WHEN status='success' THEN 1 ELSE 0 END) AS exitosos,
       SUM(CASE WHEN status='error' THEN 1 ELSE 0 END) AS fallidos,
       AVG(records_processed) AS promedio_registros
FROM sync_logs
WHERE started_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY type;

Sincronización Multi-Cuenta

¿Cómo funciona con N tiendas?

Cuando se ejecuta un comando de sync sin especificar --account, el sistema itera sobre todas las cuentas activas de todos los usuarios y lanza un Job independiente por cada una:

// Lógica del Artisan Command
$accounts = MercadolibreAccount::where('is_active', true)->get();

foreach ($accounts as $account) {
    SyncProductsJob::dispatch($account);
}

Sincronizar solo una cuenta específica

# Usando el ID de la cuenta en mercadolibre_accounts
php artisan sync:products --account=2
php artisan sync:orders --account=2
php artisan sync:customers --account=2

Aislamiento garantizado

Cada Job tiene el $account inyectado. Los queries siempre filtran por mercadolibre_account_id, garantizando que los datos de una tienda nunca se mezclen con otra.

ℹ️ Los Jobs de distintas cuentas corren en paralelo si se configura más de un worker (numprocs=2 en supervisor), acelerando la sincronización cuando hay varias tiendas.

Solución de Problemas

Los productos no se sincronizan

  1. Verificar que el Queue Worker esté corriendo: php artisan queue:listen
  2. Verificar que el Scheduler esté activo: php artisan schedule:run
  3. Revisar que la cuenta MeLi esté activa: SELECT is_active FROM mercadolibre_accounts;
  4. Revisar jobs fallidos: php artisan queue:failed
  5. Revisar el log: storage/logs/laravel.log

Error "Token expirado" durante sync

El sistema debería renovar el token automáticamente cuando expires_at < ahora + 5 minutos. Si falla:

-- Verificar estado de tokens
SELECT meli_user_id, nickname, expires_at, is_active
FROM mercadolibre_accounts
WHERE user_id = 1;

-- Forzar estado inactivo para reconectar
UPDATE mercadolibre_accounts SET is_active = 0 WHERE id = 1;

Luego reconectar la cuenta desde la UI: Mis Tiendas → Conectar con MeLi.

Webhook no llega / responde con error

  • En desarrollo, usar ngrok y actualizar la URL en el portal de MeLi developers
  • Verificar que la ruta no tenga middleware JWT (el webhook usa firma HMAC)
  • Revisar en el portal de MeLi el historial de notificaciones enviadas y su estado

La cola crece sin procesarse

# Ver tamaño de la cola
SELECT COUNT(*) as pendientes FROM jobs WHERE queue = 'default';

# Ver si hay Jobs bloqueados (attempts > 0)
SELECT id, attempts, available_at FROM jobs
WHERE attempts > 0 ORDER BY attempts DESC;

# Limpiar la cola (¡CUIDADO! Elimina todos los jobs pendientes)
php artisan queue:clear --queue=default

Comandos de diagnóstico rápido

php artisan queue:failed             # Ver jobs fallidos
php artisan queue:retry all          # Re-intentar todos los fallidos
php artisan schedule:list            # Ver cronograma de tareas
php artisan route:list --path=webhook # Verificar ruta del webhook
php artisan config:clear             # Limpiar caché de configuración
